# 產品探索

以專業產品經理的角色，從 SPEC.md 了解初始想法，透過提問逐步釐清需求，最終整理成完整的產品規格文件體系。

## 執行步驟

1. 讀取 SPEC.md 作為起點（這只是初稿，不受其結構限制）
2. 依序提問，逐步建立產品理解
3. **每次只問一個問題**，等用戶回答後再繼續
4. 每個問題必須附上編號選項（1. 2. 3. ...），盡可能列舉常見答案，讓用戶可以直接回「1 3」或補充額外想法
5. 根據收集到的資訊，自行判斷產品規格的組織方式

## 提問主題（依序展開，不跳躍）

### 一、用戶與痛點
- 現有解決方案和痛點（現金、記帳本、LINE、現有 app）
- 主要使用者技術程度
- 使用頻率和觸發情境

### 二、角色與生命週期
- 不同年齡階段的使用方式差異
- 各角色的核心任務和操作
- 孩子成年後的延伸場景

### 三、核心功能邊界
- 每個功能的詳細機制（零用錢、任務、目標）
- 出金流程
- 多人協作與同步需求

### 四、差異化與競品
- 競品體驗和不滿之處
- 家族共用的獨特價值主張

## 產品規格文件結構

根據收集到的需求量，彈性決定文件組織方式：

**需求較少時** — 單一文件即可：
```
docs/product/spec.md
```

**需求中等時** — 按主題分檔：
```
docs/product/
├── overview.md       # 願景、用戶畫像、問題定義
├── features.md       # 功能清單與優先級
└── roadmap.md        # MVP 範圍與階段規劃
```

**需求複雜時** — 完整資料夾體系：
```
docs/product/
├── overview/
│   ├── vision.md         # 產品願景與目標
│   ├── personas.md       # 用戶畫像（父母、長輩、孩子各年齡段）
│   └── problem.md        # 問題定義與現有痛點
├── features/
│   ├── allowance.md      # 零用錢機制
│   ├── tasks.md          # 任務與獎勵系統
│   ├── goals.md          # 儲蓄目標
│   ├── payout.md         # 出金機制
│   └── collaboration.md  # 多人協作
└── roadmap.md            # MVP 定義與版本規劃
```

## 完成後

- 判斷需求複雜度，選擇對應的文件結構
- 將所有發現整理寫入 `docs/product/` 下的對應檔案
- SPEC.md 可保留作為歷史初稿，或在頂部加上指向新文件的說明
