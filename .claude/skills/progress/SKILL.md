# 進度管理（PM）

`docs/progress.md` 是專案狀態的唯一出處。這個 skill 負責讓它隨時反映現況，並決定工作的先後。

## 文件格式

照 `docs/progress.md` 現有的樣子維護，不要改成別的格式：

- 開頭：`最後更新` 日期、`Current focus`、`Next action`
- 每個 Phase 一節：`## Phase N 階段進度：xx%`，下面是 5 個階段的進度條（`[#####-----] 50%`）＋負責文件路徑
- `### Phase N 開發追蹤`：checkbox 條列
- `## 文件`：各 Phase 建立或修改了哪些文件
- `## Blockers`

**條列、不用表格**：工作項目是「一項一項往下讀」，不是拿來橫向比較，所以用 checkbox 條列。

## 誰做：👤／🤖

需要使用者本人做的步驟標 👤，agent 能做的標 🤖。下面這些一律是 👤：

- 輸入密碼、登入帳號、簽署金鑰的密碼
- 法律聲明、同意條款、付款、OAuth 授權同意
- 提供只有使用者知道的資料（測試者名單、聯絡方式）
- 在實機上安裝、試用

**只在非使用者不可時才通知**：🤖 的事全部先做完、commit、更新進度，剩下的事都是 👤 時才一次通知（可用 PushNotification）。不要每完成一小項就回報或問。

## 即時更新

- 每做完一項就當場勾 checkbox、同步調整進度百分比，不要事後一次補勾
- 改完 `docs/progress.md` 一併更新 `最後更新`、`Current focus`、`Next action`

## Phase 規則

- **已上架或釘版的 Phase 不回頭改**：Phase 1 已釘版（2026-11-04）。和規格不同的實作、新發現的問題、改進點，一律記到下一個 Phase，不算前一個 Phase 未完成，也不問「要不要補做」。上架必要的修正除外。
- 迭代就是這樣：一個功能做完不代表不再碰，改進留給下一輪。

## 工作優先順序

開發追蹤裡的工作分三級，**依序做**：

1. **修正**：bug、跑版、權限錯誤（包含測試回饋）
2. **優化**：既有功能的改善（包含測試回饋）
3. **新功能**：discover 定案後才排入

同一級裡，影響資料正確或權限的排前面。測試回饋進來時，依類別插進對應的級別，**不要附在清單最後**；每項後面註明來源，例如「（測試回饋 2026-11-13）」。

discover 只發散、不排序（見 `discover` skill）；排序是這裡的事。

## 追加工作（「pm 追加」）

1. 判斷屬於哪個 Phase（已釘版的 Phase 不收新工作）
2. 判斷是修正、優化還是新功能，放進對應的級別
3. 查一下現有程式或文件是否已經部分做到，有的話在該項註明，避免重做（例如「App 很久沒開會補發，Phase 1 已經做了」）
4. 和 discover 已確認的結論相關時，註明 WD 編號
5. commit `docs(progress): ...`

## 回報

對話裡只講：改了什麼、目前卡在誰（👤 還是 🤖）、下一步。
